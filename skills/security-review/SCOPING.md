# Scoping

### Phase 1: Scope the review to the diff

A secure coding guide instructs engineers while they write a feature; this review tests one specific change right before merge. Applying an exhaustive 80-item audit to every commit causes reviewer fatigue. Inspect the changed files first, activate only the domains the change touches, and mark every other domain `not_applicable`. A frontend typography change needs no cryptographic review. A change to authentication middleware, database queries, API serializers, `package.json`, or CI workflows activates every corresponding domain.

The parent runs this phase. It reads the repository and local Git state only.

## 1. Resolve the change set

```sh
git rev-parse --show-toplevel
git status --porcelain                              # record a dirty worktree; do not review it unless asked
git merge-base <target-branch> <head>               # base SHA
git rev-parse <head>                                # head SHA
git diff --stat --find-renames <base>...<head>
git diff --name-status --find-renames <base>...<head>
git log --reverse --format='%H %an <%ae> %s' <base>..<head>
git log --format='--- %H%n%B' <base>..<head>        # full messages and trailers
git diff --find-renames <base>...<head> -- <path>   # hunks for one file
```

When a PR number or URL is given and a code-host CLI is installed and authenticated, read its context without changing anything:

```sh
gh pr view <n> --json number,title,body,author,baseRefName,headRefName,headRefOid,labels,commits,files,closingIssuesReferences
glab mr view <n> --output json
```

Use local refs first. Ask before `git fetch`, `gh pr checkout`, or any command that changes refs or the worktree. If the head commit is not available locally, say so and ask; never review a description of a change in place of its diff.

## 2. Collect intent

- **Linked requirements**: from the linked issue or ticket, list every security requirement and acceptance criterion (authentication, roles, tenant rules, signature checks, rate limits, data handling). They feed AI-02 and the human-review questions. When the ticket is not accessible, ask the user to paste its security requirements, or record that none were available.
- **Stated exceptions**: public routes, waivers, and deliberate trade-offs claimed in the PR description. AUTHN-01 requires public opt-outs to be explicit and documented.
- **Excluded paths**: generated code, vendored dependencies, snapshots, and binary fixtures. Exclude them from domain review with a reason, but keep them in scope for SECRETS and DEPS.

## 3. Detect AI authorship

Treat the change as agent-authored, and activate the `AI` domain, when any of these signals is present or the user says so:

- `Co-authored-by:` trailers that name an AI coding assistant or agent (for example Claude, Copilot, Cursor, Codex, Gemini, Devin, Jules, Aider, or OpenCode).
- "Generated with" or "Generated by" footers in commit messages or the PR body.
- Commits or PRs authored by a coding-agent bot account (`*[bot]`).
- Agent-style head branch prefixes such as `claude/`, `codex/`, `copilot/`, `cursor/`, `devin/`, or `jules/`.
- PR text, labels, or linked session transcripts that state agent involvement, or a review that runs inside an autonomous coding pipeline.

Record each signal in `review.ai_generated.signals`. Absence of signals does not prove human authorship: when provenance is unknown and the change is large or bulk-generated, ask, or run the `AI` domain anyway.

## 4. Activate domains

A domain is active when any of its signals appears in the diff. Record the triggering paths or symbols in the domain's `reason`.

| Domain | Activate when the diff touches |
|---|---|
| `AUTHN` | Route, controller, resolver, or RPC registration; login, signup, logout, password, reset, MFA or OTP, magic links, SSO or OIDC callbacks; authentication middleware, guards, and decorators; identity-provider or OAuth client configuration |
| `AUTHZ` | Any new or changed route, controller, resolver, RPC method, or admin action; lookups by identifier; `tenant_id`, `org_id`, `owner_id`, `account_id`, `workspace_id`; permission maps and policies (row-level security, OPA/Rego, Casbin, Pundit, CanCanCan, `@PreAuthorize`); workers, queue consumers, webhook processors; cookie-authenticated mutations |
| `SESSION` | Session stores and configuration, cookie attributes, JWT creation or verification, refresh tokens, logout and revocation, OAuth token handling |
| `INJECTION` | Raw SQL or raw ORM fragments, NoSQL queries, template rendering and DOM sinks, subprocess, exec, or eval, outbound HTTP to variable URLs, deserializers, input validators |
| `API` | REST, GraphQL, or gRPC routes and schemas, DTOs and serializers, OpenAPI or proto files, pagination parameters, webhook receivers, API versions and gateways |
| `FILES` | Uploads, downloads by name, path joins with input, archive extraction, XML, SVG, or Office parsing, static file serving |
| `LOGIC` | Payments, checkout, pricing, wallets, credits, balances, coupons, inventory, quotas, trials, seats, invitations, approvals, multi-step workflows, idempotency |
| `CRYPTO` | Cryptographic libraries, hashing, random token generation, key loading, TLS and HTTP client configuration, certificates |
| `SECRETS` | Always active: any change can leak a credential in code, tests, fixtures, docs, configuration, or Git history |
| `ERRORS` | Exception handlers, error responses, `try/catch` around security decisions, logging statements, audit events, logger configuration |
| `DATA` | Migrations, new columns or models, response serializers, analytics or telemetry SDKs, LLM or AI API calls, buckets, caches, backups, retention and deletion jobs |
| `DEPS` | Manifests, lockfiles, vendored code, new third-party imports, package installs in Dockerfiles or scripts |
| `CONFIG` | Dockerfiles, Compose, Kubernetes, Helm, Terraform or OpenTofu, CloudFormation, Pulumi, Bicep, web-server configuration, framework settings and profiles, CORS and security-header middleware, CI/CD workflows |
| `AI` | Any AI authorship signal from step 3 |

Path heuristics (non-exhaustive): `**/routes/**`, `**/controllers/**`, `**/handlers/**`, `**/views.py`, `**/urls.py`, `**/*resolver*`, `**/middleware*`, `**/auth*/**`, `**/policies/**`, `**/models/**`, `**/migrations/**`, `**/serializers*`, `**/schemas/**`, `**/workers/**`, `**/jobs/**`, `**/webhooks/**`, `**/*.proto`, `openapi*.{yml,yaml,json}`, `Dockerfile*`, `docker-compose*.yml`, `**/*.tf`, `**/charts/**`, `**/k8s/**`, `.github/workflows/*.yml`, `.gitlab-ci.yml`, `Jenkinsfile`, `package.json`, `*lock*`, `requirements*.txt`, `pyproject.toml`, `go.mod`, `pom.xml`, `build.gradle*`, `Cargo.toml`, `Gemfile`, `composer.json`.

Rules:

1. Every catalog domain appears in `review.json` exactly once, as `active` or `not_applicable`. A `not_applicable` domain states why the diff does not touch it.
2. Inside an active domain, every check receives a disposition. A check that cannot apply to this diff is `not_applicable` with a note (for example, AUTHN-03 when no password handling changed). SECRETS-01, SECRETS-02, and AI-02 are never `not_applicable`.
3. When in doubt, activate.
4. For diffs above roughly 1,500 changed lines or 50 files, split the review by subsystem and work in risk order: unauthenticated surfaces, authorization and tenant boundaries, money movement, secrets, CI/CD and release paths, then the rest. If time runs out, report the review as incomplete and list the subsystems not reviewed.

## 5. Scope summary

Before Phase 2, the parent records the base and head SHAs, diff statistics, excluded paths, AI signals, linked requirements, profile, and the domain activation table with reasons. This becomes the `review` object and the skeleton of `domains` in `review.json`.
